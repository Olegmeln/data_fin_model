# Конфигурация модели и конвейер сборки

Статус: спека v0.1 — 25.07.2026. Развитие Архитектуры_финмодели_v1: модель — не один
шаблон, а **конфигурационное пространство**. Конфигурация выбирается на входе
(опросником или агентом из документов) и определяет состав книги, допущения по
умолчанию, набор проверок и метрики дашборда.

## 1. Пять измерений специфики

Конфигурация модели = точка в пространстве пяти измерений. Каждое измерение
влияет на схему допущений, реестр листов и конвейер — влияние описано явно,
чтобы конфигуратор был data-driven, а не набором if-ов.

### 1.1. Статус бизнеса

| Значение | Суть | Влияние на модель |
|---|---|---|
| Действующий | факт первичен | история из выписок/отчётности; модель = продолжение тренда; допущения калибруются фактом; план-факт с первого дня |
| Новый проект | допущения первичны | ramp-up, стартовый CAPEX, деньги до выручки (runway); допущения из документов, бенчмарков и памяти предпочтений |
| Гибрид | новое направление действующего бизнеса | базовый бизнес — из факта, новое направление — как новый проект; консолидация двух контуров в одной книге |

### 1.2. Цель модели (target_use)

| Значение | Акценты книги | Обязательные листы/блоки |
|---|---|---|
| Банковское финансирование | DSCR, ковенанты, график обслуживания долга, чувствительность, консервативный сценарий | Кредит и ковенанты; чувствительность; титул под требования банка |
| Инвестор / раунд | юнит-экономика, сценарии роста, потребность в финансировании, использование средств | Дорожная карта; сценарии; презентационный слой |
| Анализ / решение | что-если, сравнение вариантов, точки безубыточности | сценарные ползунки; сравнение конфигураций |
| Запуск | вехи, кассовый разрыв, критический путь запуска | Дорожная карта ↔ CAPEX и запуск продаж; runway |
| Мониторинг / контроллинг | план-факт, алерты, пересмотр допущений | план-факт; журнал отклонений; связь с источниками |

Цель ≠ взаимоисключающий выбор: основная цель + дополнительные — book config
объединяет требования (например, банк + мониторинг после выдачи).

### 1.3. Отрасль

Уже реализовано индустриальными шаблонами (6 отраслей): статьи, слоты данных,
правила допущений, KPI. Конфигуратор добавляет: отрасль выбирает подмножество
расчётных листов (производство/закупки — для товарных отраслей, ФОТ-детализация —
для сервисных) и отраслевые бенчмарки для генерации недостающих допущений.

### 1.4. Страновая и макро-специфика

Макроблок — отдельный раздел допущений (кандидат в схему v1.1, раздел `macro`):

- валюта модели и мультивалютность (курсы — расписаниями, как ставки);
- инфляция / ИПЦ → индексация цен и расходов (сейчас `price_indexation` — строка,
  станет ссылкой на макроряд);
- ключевая ставка → ставки заимствования (`rate_formula` уже это умеет);
- налоговая система страны — уже расписаниями в `taxes`;
- страновая премия в ставке дисконтирования (build-up: безрисковая + премии).

Источник макропоказателей — публичные ряды (ЦБ, Минэк) с датой среза и
происхождением, как у любого факта. Обновление макро → пересчёт сценариев.

### 1.5. Связь с учётом и системами

| Канал | Статус | Роль в конвейере |
|---|---|---|
| Файлы: выписки CSV/XLSX/1С | готово | факт → вытеснение допущений |
| Документы: план/модель PDF/DOCX/XLSX | готово | допущения с источниками |
| Google Sheets | итерация 3 | носитель модели и источник |
| Банковские API | итерация 3 | автообновление факта |
| 1С / ERP | стратегич. | управленческий и регламентный учёт, план-факт по статьям |

Принцип: любой канал нормализуется в единую схему операций и в assumptions.v1;
происхождение (факт/допущение/формула) сохраняется на каждом значении.

## 2. Конвейер сборки модели (M-агент)

Этапы; на каждом указан контракт (что на входе/выходе) и режимы auto/AI/manual.

0. **Постановка** — статус + цель + отрасль + страна (опросник, голос, документы).
   Выход: конфигурация книги (какие листы включены, какие проверки обязательны).
1. **Сбор данных** — слоты шаблона + свободная загрузка «кинул что есть».
   Выход: реестр документов с типами.
2. **Извлечение и нормализация** — парсеры выписок; экстрактор документов
   (LLM, строго по схеме, каждый факт с источником). Выход: операции + черновик набора.
3. **Формирование допущений** — auto (профиль по умолчанию + макро + память
   предпочтений) / AI (из документов) / manual (форма). Выход: assumptions.v1 versioned.
4. **Генерация недостающего** — карта полноты (какие периоды/статьи/разделы
   закрыты, чем — фактом или допущением); интеллектуальный запрос данных;
   синтетические допущения из бенчмарков отрасли с пометкой происхождения
   и уверенности. Выход: полный набор + список «требуют уточнения».
5. **Пользовательские правки** — форма workspace v2; правка помечает поле manual;
   confirmed пополняет память предпочтений.
6. **Валидация** — арифметика, кросс-документная сверка, проверки конфигурации
   (для банка: DSCR>порога, ковенанты; для запуска: runway>0). Блокеры не пускают дальше.
7. **Сборка книги** — реестр листов по конфигурации: титул (эссенция бизнес-плана),
   дорожная карта, дашборд, допущения, сводный CF, расчётные листы, прогнозная
   отчётность (ПиУ/ДДС/баланс), кредит/ковенанты. Итоги — живыми формулами.
8. **Экспорт и публикация** — Excel, Google Sheets, живая ссылка (премиум).
9. **Жизнь модели** — контур C: план-факт из подключённых источников, пересчёт
   ковенант, сигналы об отклонениях, предложения пересмотра допущений.

Аудит (контур A) подключается на этапе 6 к нашей модели и на входе — к чужой
(И-1): извлечь набор → прогнать валидатор против пакета документов.

## 3. Влияние на код (порядок внедрения)

1. Схема v1.1 (additive): `profile.business_status`, `profile.target_use[]`,
   `profile.country`, раздел `macro` (ряды-расписания). Обратная совместимость.
2. Book config: реестр листов получает предикаты включения от конфигурации
   (цель/отрасль), а не только default_enabled.
3. Карта полноты (этап 4) — сущность + виджет; питает интеллектуальный запрос.
4. Валидации по цели (банк: DSCR/ковенанты как blocker-вопросы).
5. Макроряды: источник + дата среза + пересчёт.

Не на критическом пути до раунда — кроме того, что п.5 (книга) уже сейчас
строится data-driven, чтобы конфигуратор лёг на реестр без переписывания.

## 4. База знаний практик финмоделирования

Компилятор лучших практик (web + книги + требования банков) ведём как раздел
документации (`docs/Методология.md`, наполняется исследовательскими сессиями),
а не как разовый HTML: знания должны версионироваться в репо и быть доступны
агентам как контекст. Приоритетные темы: стандарты банков РФ к финмоделям
заёмщика, FAST/SMART-стандарты моделирования, отраслевые бенчмарки, макроисточники.
