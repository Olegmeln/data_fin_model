# Карта агентов и навыков, выбор набора, маршрутизация задач

Статус: v0.1 — 27.07.2026. Отвечает на четыре вопроса: как не зависеть от одного
вендора LLM, как выбрать оптимальный набор навыков, как вести их карту и как
сортировать задачи при изменении состава.

## 1. Независимость от вендора LLM

**Принцип:** модель — сменная деталь, навык — актив. Навык (промпт + схема
ответа + валидатор + fallback) живёт в нашем коде; кто именно генерирует
текст — настройка.

Слой `app/llm` даёт один контракт `complete(system, user, max_tokens) -> str`.
Поддержаны:

| Провайдер | Что покрывает | Настройка |
|---|---|---|
| `anthropic` | Claude (Messages API) | `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL` |
| `openai` | OpenAI, OpenRouter, DeepSeek, Together, Groq, Mistral и **любой** сервис с `/chat/completions` | `LLM_API_KEY`, `LLM_MODEL`, `LLM_BASE_URL` |
| `openai` + локальный URL | Ollama, LM Studio, vLLM — данные не покидают контур клиента | `LLM_BASE_URL=http://localhost:11434/v1`, ключ не нужен |
| `none` | ИИ выключен: работают движки правил | `LLM_PROVIDER=none` |

Добавление нового вендора = одна функция сборки запроса + одна разбора ответа
в `app/llm/client.py`. Навыки не меняются.

**Почему это важно продуктово.** Пользователь без доступа к Claude берёт
OpenRouter или локальную модель; корпоративный клиент с требованием «данные не
уходят наружу» — локальную; экономный — дешёвую. Продукт остаётся работоспособным
даже при `none`, потому что каждый LLM-навык имеет детерминированный fallback.

Проверить активную конфигурацию: `GET /api/health` → блок `llm`.

## 2. Как выбрать оптимальный набор навыков

Критерий отбора — **три фильтра подряд**:

1. **Приближает ли навык критический путь?** Если нет — в реестр инсайтов,
   не в реализацию (правило продукта, раздел «Северная звезда»).
2. **Нужна ли здесь языковая модель?** Правило: LLM применяем там, где задача
   плохо формализуется (понять произвольный документ, предложить сезонность),
   и **не применяем** там, где есть детерминированный алгоритм (посчитать NPV,
   разложить аннуитет, проверить баланс). Дешевле, быстрее, воспроизводимо —
   и это же аргумент для банков: расчёт не «придуман нейросетью».
3. **Есть ли деградация?** Каждый LLM-навык обязан иметь fallback или быть
   явно необязательным. Иначе продукт ломается у пользователя без ключа.

Из этого следует текущий баланс: **17 навыков, из них 3 зависят от LLM**
(извлечение допущений, ИИ-категоризация, уточнение допущений). Всё
ядро расчёта — детерминированное.

Признак, что навыков слишком много: два навыка производят один артефакт и оба
без явного приоритета. Признак, что мало: в `coverage()` этап конвейера имеет
ноль навыков.

## 3. Карта агентов (как ведётся)

Карта — не картинка, а **исполняемый реестр** `app/agents/registry.py`
(тот же приём, что sheet registry: состав — данные, а не код).

Каждый навык объявляет: код, роль (M/A/C), этап конвейера 0–9, что производит,
что требует, нужна ли LLM, чем заменяется, относительную стоимость, модуль.

Публикуется машиночитаемо: `GET /api/agents` — это часть контракта AFM&C,
по ней внешний агент (например, банковский) понимает, что умеет модель.

`GET /api/agents` возвращает и `coverage`: сколько навыков на роль и этап,
сколько зависят от LLM, у каких нет fallback — карта пробелов на одном экране.

### Текущее покрытие по ролям

- **M (Modelling)** — парсеры, категоризация, извлечение текста и допущений,
  опросник, мост опросника, auto-профиль, ИИ-уточнение, память предпочтений,
  сборка книги, экспорт, чувствительность.
- **A (Audit)** — валидатор, проверка ковенант, кросс-сверка наборов.
- **C (Controlling)** — план-факт (вытеснение допущений фактом).

Видимый пробел: у роли C один навык — это ожидаемо, контур сопровождения
разворачивается после пилотов (И-2 в реестре инсайтов).

## 4. Механизм сортировки задач

`plan(goal, have, llm_enabled)` в реестре: обратный проход по зависимостям от
цели + сортировка. Приоритет производителя артефакта:

```
(1) детерминированный важнее LLM
(2) меньше недостающих входов
(3) дешевле
(4) раньше по конвейеру
```

Второй критерий даёт полезный эффект: **план сам улучшается по мере накопления
данных**. Пока профиля нет — модель собирается из auto-профиля; появился
профиль опросника — планировщик переключается на мост «опросник → допущения»,
потому что у него больше не осталось недостающих входов.

Пример: `GET /api/agents?goal=exports.xlsx` вернёт упорядоченный список
навыков от допущений до Excel — с учётом того, что доступно сейчас.

### Что происходит при изменении состава навыков

- **Добавили навык** → достаточно записи в реестре: он сразу виден в карте,
  участвует в планах и в `coverage`.
- **Навык стал недоступен** (нет ключа, вендор отвалился) → `available()`
  убирает его, `resolve()` подставляет fallback, планы пересчитываются.
- **Навык подешевел/подорожал** (сменили модель) → правится `cost`,
  приоритеты меняются без переписывания вызывающего кода.
- **Появился новый этап конвейера** → навык объявляет `stage`, порядок
  выстраивается автоматически.

Тесты закрепляют именно контракт, а не конкретный список: уникальность кодов,
наличие fallback у LLM-навыков, отсутствие LLM-навыков в плане при выключенной
модели, упорядоченность плана по этапам.

## 5. Что дальше

- Журнал агентных операций (кто, когда, каким навыком, сколько токенов) —
  основа undo/redo и прозрачности (И-10).
- MCP-обвязка: те же навыки публикуются как инструменты для внешних агентов —
  реестр уже содержит всё нужное описание.
- Роутинг по стоимости: дешёвая модель на массовых задачах (категоризация),
  сильная — на извлечении из документов. Поля `cost` для этого уже есть.
