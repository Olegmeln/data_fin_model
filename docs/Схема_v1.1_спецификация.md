# assumptions.v1.1 — спецификация расширения схемы

Статус: проект спецификации, 27.07.2026. Готов к превращению в код после
разбора эталонных файлов (может уточнить состав полей).

**Принцип совместимости:** расширение строго аддитивное. Все новые разделы
имеют значения по умолчанию, старые наборы `finmodel.assumptions.v1` читаются
без миграции данных. `schema_id` поднимается до `finmodel.assumptions.v1.1`,
загрузчик принимает обе версии.

## 1. Профиль проекта: типология и представление

Расширяем `ProjectProfile`:

```python
class ProjectType(str, Enum):
    operating  = "operating"    # действующий бизнес
    greenfield = "greenfield"   # новый проект с нуля
    expansion  = "expansion"    # действующий + инвестпроект
    tree       = "tree"         # проект из подпроектов
    group      = "group"        # группа компаний
    idea       = "idea"         # инвестиционная идея
    refinance  = "refinance"    # рефинансирование
    valuation  = "valuation"    # оценка бизнеса

class DepthLevel(str, Enum):
    idea        = "idea"          # замысел, порядок цифр
    prefeasible = "prefeasible"   # КП, прикидки, аналоги
    feasible    = "feasible"      # сметы, договоры
    execution   = "execution"     # идёт реализация
    operation   = "operation"     # эксплуатация, есть факт

class DisplayLevel(str, Enum):
    year    = "year"      # по умолчанию
    quarter = "quarter"
    month   = "month"

class ProjectProfile(Strict):
    name: str
    project_type: ProjectType = ProjectType.greenfield
    depth_level: DepthLevel | None = None      # None = определяет агент
    display_level: DisplayLevel = DisplayLevel.year
    industry: str | None = None
    country: str = "RU"
    location: str | None = None
    currency: str = "RUB"
    horizon_years: int = Field(3, ge=1, le=50)  # было 5 → стало 3
    model_start: date | None = None
```

Прежнее строковое поле `project_type` («строительство → производство →
реализация») переезжает в `description: str | None` — свободное пояснение.

## 2. Дерево подпроектов

Рекурсивная структура: узел содержит собственные допущения и список детей.

```python
class SubProject(Strict):
    code: str                                  # стабильный идентификатор узла
    name: str
    project_type: ProjectType = ProjectType.greenfield
    start_month: int = Field(0, ge=0)          # смещение от старта корня
    assumptions: "AssumptionSet"               # рекурсия: тот же документ
    consolidate: bool = True                   # входит ли в консолидацию корня
    links: list["ProjectLink"] = []

class LinkKind(str, Enum):
    output_to_input = "output_to_input"  # выпуск узла A → сырьё узла B
    funds           = "funds"            # транш/взнос из A финансирует B
    service         = "service"          # A оказывает услугу B (внутригрупповой оборот)

class ProjectLink(Strict):
    kind: LinkKind
    from_code: str
    to_code: str
    share_pct: float = Field(100, ge=0, le=100)
    eliminate: bool = True   # исключать ли из консолидированной отчётности
```

В корневом `AssumptionSet` добавляется `subprojects: list[SubProject] = []`.

**Правила расчёта.** Каждый узел считается независимо своим движком; корень
получает суммы детей плюс собственные ряды. Внутригрупповые обороты с
`eliminate=True` вычитаются из консолидированной выручки и расходов. Метрики
(NPV, IRR, DSCR) считаются и на узле, и на корне: банк часто смотрит конкретный
подпроект под свой транш.

**Ограничения:** глубина дерева ≤ 3 (проект → подпроект → этап), защита от
циклических ссылок в `links`, коды узлов уникальны в пределах корня.

## 3. Оборотный капитал

Ключ к тому, чтобы ДДС и ПиУ расходились предсказуемо.

```python
class WorkingCapital(Strict):
    receivable_days: float = Field(0, ge=0)      # отсрочка покупателям
    payable_days: float = Field(0, ge=0)         # отсрочка поставщиков
    inventory_days: float = Field(0, ge=0)       # запасы в днях себестоимости
    advances_received_pct: float = Field(0, ge=0, le=100)   # авансы от покупателей
    advances_paid_pct: float = Field(0, ge=0, le=100)       # авансы поставщикам
    source: str = "industry"   # industry | user | extracted
```

По умолчанию заполняется среднеотраслевыми значениями (бенчмарки И-9),
помечается жёлтым; пользовательская правка делает поле зелёным.

**Связь с ДДС:** денежный поток = начисление − прирост дебиторки + прирост
кредиторки − прирост запасов + прирост авансов полученных − авансы выданные.
Если все дни равны нулю — ДДС совпадает с ПиУ (поведение по умолчанию).

## 4. Расходы на продажу

Выделяются из общего `opex` в отдельный раздел — у них другая природа
(привязка к объёму, а не к периоду).

```python
class SalesCostItem(Strict):
    name: str
    pct_of_revenue: float = Field(0, ge=0, le=100)
    per_unit: float = Field(0, ge=0)          # на единицу продукции
    monthly_amount: float = Field(0, ge=0)    # фиксированная часть
    product: str | None = None                # привязка к продукту/каналу

class SalesCosts(Strict):
    items: list[SalesCostItem] = []
```

Типовые статьи: комиссия площадок, эквайринг, логистика сбыта, упаковка,
маркетинг, бонусы менеджерам, возвраты и рекламации.

## 5. Основные средства по объектам

Заменяет плоский `capex.depreciation_months` на объектный учёт.

```python
class DepreciationMethod(str, Enum):
    straight = "straight"      # линейный
    declining = "declining"    # уменьшаемого остатка
    none = "none"              # не амортизируется (земля)

class FixedAsset(Strict):
    name: str
    group: str | None = None               # здания, оборудование, транспорт…
    cost: float = Field(ge=0)
    vat_included: bool = False
    commissioning_month: int = Field(0, ge=0)   # месяц ввода в эксплуатацию
    useful_life_months: int = Field(60, ge=1)
    method: DepreciationMethod = DepreciationMethod.straight
    salvage_pct: float = Field(0, ge=0, le=100)
    maintenance_pct_year: float = Field(0, ge=0)   # ремонт, % от стоимости в год
    disposal_month: int | None = None              # выбытие
    subproject: str | None = None                  # код узла дерева

class FixedAssets(Strict):
    items: list[FixedAsset] = []
```

`capex.items` остаётся для затрат, не создающих ОС (проектирование, пусконаладка,
оборотные вложения). Амортизация считается по `fixed_assets`.

## 6. План набора персонала

Расширение текущего `staff`: не только оклады, но и график найма.

```python
class PayrollRole(Strict):
    name: str
    department: str | None = None
    subproject: str | None = None
    monthly_salary: float = Field(ge=0)      # оклад gross на человека
    bonus_pct: float = Field(0, ge=0)        # премия, % от оклада
    hiring_plan: list[HiringPoint] = []      # график численности
    indexation_pct_year: float = Field(0, ge=0)   # ежегодная индексация

class HiringPoint(Strict):
    month: int = Field(ge=0)
    headcount: float = Field(ge=0)   # численность НА этот месяц (ступенька)

class Staff(Strict):
    roles: list[PayrollRole] = []
    contributions_included: bool = False
    ndfl_pct: float = Field(13, ge=0, le=100)   # для расчёта «на руки»
```

Прежняя плоская форма (`count`, `start_month`, `end_month`) конвертируется в
`hiring_plan` из одной-двух точек при чтении старых наборов.

## 7. НДС и выбор налогового режима

```python
class TaxRegime(str, Enum):
    osno   = "osno"
    usn6   = "usn6"
    usn15  = "usn15"
    psn    = "psn"     # патент
    npd    = "npd"     # самозанятость
    eshn   = "eshn"    # сельхозналог
    special = "special" # ТОСЭР, СЭЗ, ОЭЗ — ставки задаются вручную

class Vat(Strict):
    enabled: bool = True                    # у УСН/НПД — False
    rate: RateSchedule                      # расписание ставки
    input_vat_on_capex: bool = True         # вычет по капвложениям
    input_vat_on_opex_pct: float = Field(80, ge=0, le=100)  # доля закупок с НДС
    refund_lag_months: int = Field(3, ge=0) # лаг возмещения из бюджета
    reduced_rate_products: list[str] = []   # продукты по льготной ставке

class TaxRegimeChoice(Strict):
    """Результат подбора режима: рекомендация + обоснование."""
    selected: TaxRegime
    recommended: TaxRegime | None = None
    rationale: str | None = None            # текст для бизнес-плана
    compared: dict[str, float] = {}         # режим → налоговая нагрузка за горизонт
    confirmed_by_user: bool = False
```

### Критерии подбора режима

Агент считает и предлагает, пользователь подтверждает:

| Критерий | Правило |
|---|---|
| Лимит выручки | Выручка за год выше лимита УСН → только ОСНО |
| Численность и ОС | Превышение лимитов по штату и остаточной стоимости ОС → ОСНО |
| Доля расходов | Расходы > ~60–70% выручки → УСН 15% выгоднее УСН 6% |
| НДС-контрагенты | Покупатели на ОСНО требуют НДС → ОСНО, иначе теряем клиентов |
| Возмещение НДС с CAPEX | Крупные капвложения → ОСНО может выиграть за счёт возмещения |
| Вид деятельности | Патент/ЕСХН доступны не всем — проверка по перечню |
| Региональные льготы | Пониженные ставки УСН, ТОСЭР/ОЭЗ — по региону |

Все лимиты и ставки — не константы в коде, а справочник с датой актуальности
(раздел макро, см. §8): они меняются законом.

## 10. Влияние на движок

| Раздел | Что добавляется в расчёт |
|---|---|
| `subprojects` | Рекурсивный расчёт узлов + консолидация с элиминацией |
| `working_capital` | Разрыв между ПиУ и ДДС; строки дебиторки/кредиторки в балансе |
| `sales_costs` | Отдельная группа в P&L между выручкой и валовой прибылью |
| `fixed_assets` | Амортизация по объектам и методам; ремонты; выбытие |
| `staff.hiring_plan` | Численность по месяцам → ФОТ → взносы → НДФЛ |
| `vat` | Начисленный / к вычету / к уплате / возмещение с лагом; влияет на CF |
| `display_level` | Агрегация месячных рядов в кварталы и годы для представления |
| `macro` | Индексация рядов, ставка дисконтирования, ставки кредитов |

Порядок реализации: сначала `working_capital` и `vat` (они меняют ДДС и
делают отчётность корректной), затем `fixed_assets` и `staff.hiring_plan`
(детализация), затем `subprojects` (архитектурно самое крупное), затем `macro`.
