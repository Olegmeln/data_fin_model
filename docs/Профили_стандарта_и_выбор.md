# Профили стандарта, выбор профиля и интерфейс уточнения

Статус: v0.1 — 09.09.2026, проектный документ (реализации ещё нет).
Отвечает на вопрос: как жить с тем, что **стандартов заполнения несколько**,
и пользователь вправе настроить свой — не потеряв при этом контракт AFM&C.

---

## 1. Противоречие, с которого всё началось

Сегодня в проекте сосуществуют два несовместимых описания книги:

| | Реестр листов платформы | Навык `dfm-standard` |
|---|---|---|
| Листов | 15 | 26 |
| Коды | `cover`, `assumptions`, `cf`, `pl`, `capex` | `Cover`, `Business_Model`, `Timeline`, `Structure` |
| Подписи | русские (`Обложка`, `ПиУ`) | английские, они же коды |
| Раскладка расчётного листа | не зафиксирована | жёсткий контракт: строки 7–18 допущения, 20–23 шапка, F:AO периоды |
| Реестр статей | нет | `Structure` + `tblSTRUCT_Items` |
| Где живёт | `backend/app/finmodel/book/registry.py` | личный скилл, вне репозитория |

Соблазн — объявить один из них правильным. **Это ошибка.** Оба стандарта
осмысленны и адресованы разным потребителям: 15 листов — компактная книга под
экспорт и API, 26 листов — развёрнутая модель под ручную работу аналитика с
реестром статей и прослеживаемостью. Банк захочет третий, инвестфонд —
четвёртый.

Правильный вывод другой: **раскладка книги не должна быть кодом.** Она должна
быть данными — ровно тем же приёмом, каким уже сделаны sheet registry и skill
registry («состав — данные, а не код»).

## 2. Что именно является контрактом

Разделяем три слоя. Путаница между ними и породила противоречие.

| Слой | Что фиксирует | Меняется ли | Артефакт |
|---|---|---|---|
| **Данные** | какие допущения и с какой семантикой | нет — контракт | `assumptions.v1` |
| **Адресация** | коды листов, имена именованных диапазонов (`RevenueRow`, `NetCFRow`, `NPV`, `DSCRmin`) | нет — контракт | ядро `standard.v1` |
| **Представление** | сколько листов, подписи, порядок, цвета, локаль, раскладка строк | **да — профиль** | инстанс `standard.v1` |

Формулировка правила: *внешний агент адресует модель по кодам и именованным
диапазонам; всё остальное он не обязан знать.* Значит расхождение 15↔26 —
не противоречие, а два профиля одного контракта, при условии что оба содержат
обязательное ядро.

**Уровни соответствия:**

- `core` — реализованы все листы и диапазоны обязательного ядра. Модель
  машиночитаема, аудит и контроллинг работают.
- `extended` — ядро плюс дополнительные листы профиля.
- `custom` — профиль пользователя; ядро обязано сохраняться, иначе профиль
  невалиден и валидатор это скажет.

## 2а. Отношение к И-7 (конфигуратор модели)

Половина этой темы уже запаркована: И-7 и спека
`Конфигурация_модели_и_конвейер.md` описывают конфигуратор — пять измерений
специфики (статус бизнеса / цель / отрасль / страна / каналы учёта),
определяющих состав книги, дефолты и проверки. Настоящий документ его **не
заменяет и не дублирует**; он закрывает то, чего в И-7 нет.

| Вопрос | Кто отвечает |
|---|---|
| Какие листы **включить** под эту задачу и отрасль | конфигуратор И-7 (предикаты включения над реестром) |
| Какие листы вообще **существуют**, как называются, в каком порядке, на каком языке, с какой раскладкой строк | **профиль `standard.v1`** |
| Что нельзя менять никогда (ядро кодов и диапазонов) | **профиль `standard.v1`**, поле `conformance` |
| Что делать, когда вход неоднозначен | **контракт `Clarification`** (§5) |

Метафора: профиль задаёт алфавит и типографику, конфигуратор — какие слова из
этого алфавита писать. Сегодня оба вопроса смешаны в одном литеральном кортеже
в `book/registry.py`, и именно поэтому 26-листовый стандарт не смог там
поселиться и уехал в отдельный скилл.

Порядок внедрения из §3 спеки И-7 при этом не меняется: профиль ложится на тот
же data-driven реестр, ради которого он и делался.

## 3. Дескриптор `standard.v1`

Декларативный, наследуемый, версионируемый. Хранится как JSON рядом с
`assumptions.v1.schema.json`.

```jsonc
{
  "standard_id": "dfm.full.v26",
  "title": "DFM развёрнутая модель, 26 листов",
  "version": "1.0.0",
  "extends": "dfm.core.v1",          // наследование: только дельта
  "locale": "en",
  "conformance": "extended",

  "sheets": [
    { "code": "timeline", "title": "Timeline", "group": "front",
      "order": 30, "tab_color": "#1F3864", "builder": "build_timeline" },
    { "code": "structure", "title": "Structure", "group": "input",
      "order": 60, "tab_color": "#2E75B6", "builder": "build_structure" }
  ],

  "calc_layout": {                    // контракт расчётного листа
    "header_rows": 5,
    "assumptions_block": { "from": 7, "to": 18 },
    "period_label_row": 20,
    "period_id_row": 21,
    "flag_active_row": 22,
    "columns_header_row": 23,
    "first_period_col": "F",
    "period_count": 36
  },

  "naming": {
    "assum_id_pattern": "A_[0-9]{3}",
    "named_ranges": { "revenue": "RevenueRow", "net_cf": "NetCFRow",
                      "npv": "NPV", "dscr_min": "DSCRmin" }
  },

  "controls": [
    { "code": "balance_identity", "severity": "error" },
    { "code": "no_literal_in_period_row", "severity": "error" },
    { "code": "assumption_pulled_once", "severity": "warning" }
  ]
}
```

Что это даёт немедленно:

- `dfm.core.v1` — текущие 15 листов, записанные как профиль. Движок не меняется,
  меняется источник состава.
- `dfm.full.v26` — навык `dfm-standard`, выраженный как `extends: dfm.core.v1`
  плюс 11 листов и `calc_layout`. Скилл перестаёт быть отдельной истиной и
  становится **документацией к профилю**.
- `bank.<name>.v1` — профиль под требования конкретного банка. Вот это уже
  продаётся: банк получает не «модель», а модель в своём формате.

## 4. Навык выбора профиля

Добавляется в `app/agents/registry.py`, этап 0 — до опросника:

```python
Skill("select_standard", "Выбор профиля стандарта", "M", 0,
      produces=("standard",), requires=(),
      module="app.finmodel.standards.select",
      tags=("standard", "deterministic")),
Skill("clarify_standard", "Уточнение профиля у пользователя", "M", 0,
      produces=("standard",), requires=("standard.candidates",),
      module="app.finmodel.standards.clarify",
      tags=("standard", "interactive")),
```

Выбор **детерминированный**, по приоритету — это принципиально, потому что
действует правило проекта «LLM применяем там, где задача плохо формализуется,
и не применяем там, где есть алгоритм»:

1. `standard_id` передан явно (API, MCP-вызов, флаг) → берём его.
2. Профиль воркспейса/организации задан → берём его. *(доступно после auth)*
3. Выводится из цели: `bank_credit` → `bank.*`; `investor` → `dfm.full.v26`;
   `controlling` → `dfm.core.v1`; `export` → `dfm.core.v1`.
4. Отрасль из опросника сужает список кандидатов.
5. Кандидатов больше одного → `clarify_standard`.
6. Ничего не известно → `dfm.core.v1` как безопасный минимум, с пометкой
   «принято по умолчанию».

Пункт 6 обязателен: **план никогда не блокируется**. Внешний агент, работающий
без человека, всегда получает результат и всегда знает, что было допущено.

## 5. Интерфейс уточнения запроса

Здесь стоит сделать шаг шире, чем требует выбор стандарта. Уточнение нужно не
только профилю: извлечение допущений тоже упирается в неоднозначность («в
документе НДС 20% и 18% в разных таблицах — какой брать»). Значит уточнение —
не функция одного навыка, а **общий контракт возврата**.

Любой навык вправе вернуть вместо артефакта объект `Clarification`:

```jsonc
{
  "kind": "clarification",
  "id": "standard.choice",
  "question": "Для чего собираем модель?",
  "why": "От этого зависит состав листов и раскладка книги",
  "multi": false,
  "options": [
    { "id": "bank_credit", "label": "Заявка в банк",
      "implies": { "standard_id": "bank.generic.v1" } },
    { "id": "investor",    "label": "Инвестору / фонду",
      "implies": { "standard_id": "dfm.full.v26" } },
    { "id": "controlling", "label": "Внутренний контроллинг",
      "implies": { "standard_id": "dfm.core.v1" } }
  ],
  "default": "controlling",
  "blocking": false
}
```

Три свойства делают его пригодным и для человека, и для агента:

- **`default` есть всегда.** `blocking: false` означает: не дождались ответа —
  применили дефолт, записали в provenance, пошли дальше. Ночной прогон не
  висит.
- **`implies` машиночитаем.** Ответ не текст, а набор параметров. Внешний агент
  выбирает `id`, не разбирая человеческий язык.
- **Один объект — три отрисовки.** В веб-интерфейсе модалка; через MCP —
  структура, которую вызывающий агент показывает пользователю; в CLI — список.
  Реализация одна.

Это часть контракта AFM&C наравне с `/api/agents`: внешний агент должен уметь
не только вызвать навык, но и корректно ответить на его встречный вопрос.

## 6. Как снимается исходное противоречие

Пошагово, без унификации и без потери ни одного из двух стандартов:

| Шаг | Действие | Результат |
|---|---|---|
| 1 | `standards/dfm.core.v1.json` — текущие 15 листов как профиль | Ничего не сломано, состав стал данными |
| 2 | `book/registry.py` читает профиль вместо литерального кортежа | Движок параметризован |
| 3 | Выделено обязательное ядро: коды листов + именованные диапазоны | Появился измеримый `conformance` |
| 4 | `standards/dfm.full.v26.json` — 26 листов через `extends` | Скилл `dfm-standard` перестал противоречить платформе |
| 5 | Навык `select_standard` + контракт `Clarification` | Профиль выбирается, а не зашит |
| 6 | Валидатор проверяет `conformance` профиля | Пользовательский профиль нельзя сломать незаметно |
| 7 | `GET /api/standards` | Профили публикуются так же, как навыки |

Шаги 1–3 не требуют ни аутентификации, ни ключа LLM — их можно делать сразу.
Шаги 5–7 имеет смысл делать вместе с MCP-обвязкой.

## 7. Побочный эффект, ради которого это и стоит делать

Профиль — единица, которую можно **продать и передать**. Банк, опубликовавший свой
`bank.sber.v1`, получает поток моделей в своём формате от всех, кто пользуется
платформой. Это ровно тот механизм, которым XBRL стал обязательным: не
уговорами, а тем, что принимающая сторона объявила формат.

Пока стандарт один и зашит в код, продавать нечего. Как только профилей
много и они декларативны — появляется и предмет продажи, и причина для банка
участвовать.
