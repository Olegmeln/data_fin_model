# Миграции базы данных (Alembic)

Схема БД версионируется Alembic. URL подключения берётся из настроек
приложения (`DATABASE_URL` / `POSTGRES_URL`), отдельно ничего настраивать
не нужно. Все команды выполняются из каталога `backend/`.

## Повседневные команды

```bash
alembic upgrade head        # накатить все миграции
alembic check               # схема БД соответствует моделям?
alembic history             # список ревизий
alembic downgrade -1        # откатить одну миграцию
```

## Изменение схемы

1. Правим модели в `app/models.py`.
2. Генерируем миграцию: `alembic revision --autogenerate -m "что изменилось"`.
3. **Читаем сгенерированный файл** в `alembic/versions/` — автогенерация
   не видит переименования (считает их drop+create) и данные не переносит.
4. Проверяем: `alembic upgrade head`, затем `alembic check` и `pytest`.

## Как это уживается с init_db

Для локальной разработки и SQLite приложение по-прежнему создаёт схему
через `create_all` при старте — это удобно и идемпотентно. После создания
`init_db` ставит штамп `alembic stamp head`, поэтому на такой базе
`alembic upgrade head` работает корректно и накатывает только новое.

На Postgres (Vercel/Neon) при выкате новой версии со сменой схемы порядок:
`alembic upgrade head` → деплой приложения.

CI проверяет миграции на каждом push: `upgrade head` на чистой базе
и `alembic check` (расхождение моделей и миграций валит сборку).
