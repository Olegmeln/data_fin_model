# Протокол финансового моделирования

Единый свод правил, которым следует движок финмодели — и агенты в Kaggle-ноутбуке,
и продуктовый бэкенд `data_fin_model`. Цель: из разнородных входов (выписки, сметы,
баланс, штат, 1С/ERP) собрать корректную, обновляемую и расширяемую модель, где у
каждой цифры известно происхождение (факт / допущение), а структура подобрана под тип
бизнеса и меняется по запросу пользователя.

Документ — источник истины: на него ссылаются writeup capstone и README продукта.

---

## 0. Универсальные принципы

- **Три взаимоувязанных контура:** P&L (прибыли/убытки), денежный поток (cash flow) и
  накопленный остаток. Внутренние переводы исключаются из P&L и потока (это движение
  между своими счетами, не доход/расход).
- **Драйверы отдельно от расчётов.** Входы (выручка, доли затрат, ставки, CAPEX,
  кредит) — редактируемые; всё остальное — формулы от них. Ничего не «зашивается»
  числом в формулы: ключевые входы имеют именованные диапазоны (`BaseRevenue`,
  `CogsPct`, `LoanAmount`, `DiscountRate`…).
- **Происхождение каждой ячейки: `факт` или `допущение`.** Факт (из документа)
  вытесняет допущение за тот же период и статью; правка пользователя приоритетнее
  сгенерированного допущения и приоритетнее повторного опросника.
- **Цветовой стандарт:** синие входы, чёрные формулы, зелёные межлистовые ссылки.
- **Горизонт и гранулярность:** помесячно, горизонт 12–36+ мес.; валюта и дата старта —
  явные параметры. Расходы хранятся положительными, знак задаёт направление.
- **Сценарии и чувствительность:** База / Пессимист / Оптимист поверх одних входов;
  матрица чувствительности по ключевым драйверам (выручка × себестоимость).
- **Инвестиционная рамка:** любой бизнес — как инвестпроект: CAPEX + финансирование →
  NPV / IRR / срок окупаемости по проектному потоку (без финансирования), ставка
  дисконтирования — вход.

## 1. Приём и классификация содержимого документов

Любой приложенный документ проходит: **определение типа → извлечение → классификация →
запись как факт**. Источники и что из них берём:

| Документ | Извлекаем | Целевой блок |
|---|---|---|
| Банковская выписка (CSV/XLSX/PDF/1С/ZIP) | операции: дата, сумма, направление, контрагент, назначение | Факт P&L / поток |
| Смета / счета на CAPEX (XLSX/PDF) | позиции, стоимость, срок, амортизация | CAPEX |
| Баланс (XLSX/PDF) | активы/пассивы, остатки | Стартовые остатки, сверка |
| Штатное расписание | роль, кол-во, оклад, взносы | ФОТ |
| Данные по активу (участок/кадастр) | площадь, стоимость, назначение | CAPEX / залог |
| 1С-обмен / ERP / SQL-хранилище | операции и обороты в объёме | Факт (пакетно) |

**Классификация операций — каскад, побеждает первый сработавший:**
`выученные правила (память) → ключевые слова шаблона → ИИ (structured output) → фолбэк`.
Операции с уверенностью ниже порога помечаются «требует подтверждения»; подтверждение
создаёт правило `контрагент → статья` и переразмечает похожие. Дубликаты отсекаются по
хэшу операции (безопасна повторная и кросс-форматная загрузка).

**Правило:** извлечённый факт всегда предпочтительнее допущения; если документ
нераспознан (скан без текста, чужой формат) — не выдумывать, а вернуть понятную ошибку
и предложить альтернативу (OCR / другой формат).

## 2. Генерация недостающих данных (допущения)

Если данных нет или их недостаточно — модель **достраивается допущениями**, а не
остаётся пустой. Порядок:

1. **Оценка достаточности.** По целевой структуре считаем покрытие: какие блоки/периоды
   закрыты фактом, где дыры → формируем точечные вопросы пользователю (industry, драйверы,
   CAPEX, кредит, ковенанты).
2. **Отраслевые дефолты.** Стартовые доли затрат, сезонность, налоговый режим берутся из
   шаблона отрасли (услуги, розница/e-com, общепит, SaaS, производство/опт, инвестпроект).
3. **Генерация из ответов опросника:** разгон выручки на старте, распределение CAPEX по
   месяцам, аннуитет по кредиту, индексация.
4. **ИИ-уточнение (опц.):** при наличии ключа модель уточняет допущения (сезонность,
   реалистичные доли, специфика из параметров пользователя).
5. **Провенанс = `допущение`.** Как только приходит факт за период — допущение вытесняется
   им (на дашборде пунктир сменяется сплошной линией), но сохраняется в истории.

**Правило:** каждое допущение объяснимо (источник: опросник / отрасль / ИИ / правка
пользователя) и заменяемо фактом.

---

## 3. Определение оптимальной структуры модели

Структура подбирается под тип бизнеса, а не «одна на всех». Базовый каркас есть всегда,
дополнительные листы включаются по признакам:

- **Всегда:** Допущения · Модель (P&L помесячно) · Денежный поток · Дашборд (KPI) ·
  Годовая сводка.
- **Инвестпроект / девелопмент:** + CAPEX и смета, + земля/актив, + Финансирование
  (кредит-аннуитет), + NPV/IRR/окупаемость, + Чувствительность.
- **Трудоёмкий бизнес (услуги/общепит):** + Штатное расписание (ФОТ с взносами).
- **SaaS / подписка:** + метрики MRR/ARR, отток, CAC/LTV, когорты.
- **Розница / опт:** + оборачиваемость запасов, закупки, логистика.

**Правило выбора:** `industry + наличие CAPEX/кредита/актива → набор листов`. Минимум
шума: не показывать пустые блоки, включать лист только когда для него есть факт или
осмысленное допущение.

---

## 4. Адаптация и расширение под запрос пользователя

Модель — живая и расширяемая, а не финальный снимок:

- Пользователь может **добавить/убрать статью, месяц, лист** (например «добавь расчёт
  окупаемости оборудования» или «разбей ФОТ по отделам») — движок достраивает блок,
  сохраняя связи и именованные диапазоны.
- **Правки пользователя — высший приоритет** над авто-допущениями и опросником; они не
  затираются пересборкой.
- Изменение драйвера пересчитывает всю модель (формулы), не ломая факт.
- Любой лист остаётся экспортируемым (.xlsx / Google Sheets) с живыми формулами.

**Правило:** расширение не должно нарушать провенанс (факт остаётся фактом) и увязку трёх
контуров.

---

## 5. Валидация и sanity-checks

Перед показом/экспортом модель обязана пройти проверки:

- Внутренние переводы исключены из P&L и потока.
- Знаки корректны (расход положительный, направление задаёт роль); суммы вида
  `1 234,56` и разные кодировки разобраны верно.
- Накопленный остаток непрерывен; кассовый разрыв виден явно, а не «прячется».
- Дедупликация операций (хэш) отработала; нет задвоений при повторной загрузке.
- NPV/IRR/окупаемость посчитаны на проектном потоке (без финансирования) и правдоподобны.
- Доля операций «требует подтверждения» и средняя уверенность категоризации — в отчёте.
- Инсайты **заземлены**: только на посчитанных числах, без выдуманных значений; при
  горизонте < 2 мес. — пометка о низкой уверенности.

---

## 6. Таксономия статей

Универсальный справочник (доход / расход / инвестиции / финансирование / перевод):
выручка от продаж, прочие поступления, закупка товаров/материалов (COGS), ФОТ, налоги и
взносы, аренда и коммунальные, маркетинг, сервисы и подрядчики, логистика, банковские
услуги, выплаты собственнику, CAPEX, кредит/заём (поступление/погашение), внутренний
перевод, прочие расходы. Расширяется под отрасль.

## 7. Где это реализовано в коде

| Правило протокола | Модуль |
|---|---|
| Приём/парсинг выписок (CSV/XLSX/PDF/1С/ZIP) | `backend/app/parsers/` |
| Каскад классификации + память | `backend/app/categorization/` |
| Сборка модели, дашборд, NPV/IRR | `backend/app/finmodel/builder.py` |
| Именованные входы, сценарии, чувствительность | `backend/app/finmodel/excel_export.py` |
| Отраслевые шаблоны, опросник, достаточность | `backend/app/finmodel/industries.py`, `survey.py` |
| Допущения и провенанс | `backend/app/models.py` (Assumption), `finmodel/` |
| Синхронизация с Google Sheets | `backend/app/finmodel/sheets_sync.py` |
| Агенты (Parsing/Categorization/Model/Insight/Orchestrator) | `fin_agent_capstone.ipynb` |

> Разделы 1–4 — это ровно те четыре поведения движка, к которым идём в MVP: читать и
> классифицировать документы, достраивать недостающее допущениями, выбирать структуру и
> менять её под запрос. Протокол фиксирует правила; реализация подтягивается к ним
> итерациями.
