# Протокол старта проекта и подпроекта

Статус: v1.0 — 09.09.2026. Отвечает на четыре вопроса, которые каждый раз
задаются заново: **кто что создаёт**, **как называется**, **что обязано
существовать до первой строки кода** и **где это живёт**.

Протокол исполняемый: он же лежит навыком `project-bootstrap` в плагине
`dfm-dev`, поэтому Claude следует ему без напоминания.

---

## 1. Роли: кто что создаёт

Разделение не организационное, а техническое — оно вытекает из того, какими
правами кто фактически обладает.

| Артефакт | Создаёт | Почему так |
|---|---|---|
| Репозиторий на GitHub | **Пользователь** | У Claude в облачном контейнере нет ни `gh`, ни push-кредов — только чтение публичных репозиториев |
| Локальная папка проекта | **Пользователь** (клон через GitHub Desktop) | Там же, где остальные проекты: `C:\Users\<user>\<repo>` |
| Подключение папки к сессии | **Пользователь** (по запросу Claude) | Разрешение выдаётся на машине, одним диалогом |
| Каталоги **внутри** репозитория | **Claude** | Создаются самой записью файлов; отдельный `mkdir` не нужен |
| Содержимое файлов, структура, доки | **Claude** | Это и есть предмет работы |
| Коммит и push | **Пользователь** | GitHub Desktop; Claude пишет файлы, но не коммитит |

**Следствие:** Claude никогда не говорит «создай репозиторий и скажи, когда
готово» в середине работы. Вопрос о репозитории решается **до** начала —
пунктом 4 этого протокола.

---

## 2. Два режима доставки

Режим определяется одним фактом: подключена ли папка проекта к сессии.

| | Папка подключена | Папка не подключена |
|---|---|---|
| Как попадают файлы | Claude пишет прямо в рабочую копию | Claude отдаёт патч `NNNN-*.patch` |
| Что делает пользователь | Смотрит diff и коммитит в GitHub Desktop | Кладёт в `files\`, `git am`, затем коммит |
| Когда уместно | Норма. Быстрее, diff виден сразу | Машина недоступна, либо нужен готовый коммит с сообщением |

Прямая запись — режим по умолчанию, потому что GitHub Desktop **не умеет
применять патчи**: `git am` требует терминала, и это лишний шаг.

Правило безопасности прямой записи: **Claude создаёт новые файлы и правит
только те, о которых договорились**. Если в рабочей копии есть незакоммиченные
изменения — Claude их не трогает и предупреждает об этом до записи.

## 3. Именование

| Что | Формат | Пример | Почему |
|---|---|---|---|
| Репозиторий | `snake_case` | `data_fin_model`, `semcode_prompt` | Уже сложившаяся практика |
| Плагин | `kebab-case` | `dfm-dev` | Имя становится namespace скиллов: `/dfm-dev:patch-flow` — требование Claude Code |
| Скилл | `kebab-case` | `project-bootstrap` | Имя папки = имя команды |
| Документ в `docs/` | Русский, `_` вместо пробелов | `Карта_агентов_и_навыков.md` | Уже сложившаяся практика |
| Патч | `NNNN-краткое-описание.patch` | `0011-plugin-dfm-dev.patch` | Сквозная нумерация по репозиторию, 4 цифры |
| Код в реестре | `snake_case`, латиница | `extract_assumptions`, `capex` | **Это контракт.** Код стабилен навсегда; подпись и порядок — нет |

Последняя строка — самая важная. Подпись листа можно перевести, порядок
переставить, цвет вкладки сменить. **Код — нельзя**: по нему внешний агент
адресует лист, а внешние агенты — это и есть продукт.

## 4. Новый репозиторий или подкаталог существующего

Три критерия. Новый репозиторий заводится, **только если все три — «да»**:

1. **Свои потребители.** Артефактом пользуется кто-то, кроме этого проекта?
2. **Свой цикл релиза.** Он версионируется и выпускается отдельно?
3. **Своя лицензия.** Права на него отличаются от прав на основной репозиторий?

Хотя бы одно «нет» → подкаталог. Проверка на текущих случаях:

| Артефакт | Потребители | Релиз | Лицензия | Решение |
|---|---|---|---|---|
| `dfm-dev` (внутренний плагин) | нет | нет | нет | `plugins/dfm-dev/` в `data_fin_model` |
| `dfm` (продуктовый плагин) | да | да | да | отдельно — но **не сейчас**, см. ниже |
| Маркетплейс | да | да | да | отдельный репозиторий, когда появится что публиковать |

**Разделение репозиториев можно откладывать бесплатно.** Маркетплейс умеет
брать плагин из подкаталога чужого репозитория источником `git-subdir`:

```json
{
  "name": "dfm",
  "source": {
    "source": "git-subdir",
    "url": "https://github.com/Olegmeln/data_fin_model.git",
    "path": "plugins/dfm"
  }
}
```

То есть плагин живёт в продуктовом репозитории и публикуется из отдельного
маркетплейс-репозитория. Split делается тогда, когда лицензии реально
разойдутся, а не заранее.

## 5. Обязательный стартовый комплект — 8 пунктов

Ни одной строки кода до того, как это существует. Порядок важен: каждый
следующий пункт опирается на предыдущий.

1. **`README.md`** — что это, для кого, как запустить. Три абзаца, не больше.
   Пишется первым: если не формулируется — проект ещё не продуман.
2. **`LICENSE`** — решение принимается **на старте**. Откладывание стоит
   дорого: `data_fin_model` сейчас проприетарен и одновременно публичен, и это
   блокирует публикацию плагина (см. §7).
3. **`.gitattributes`** — `* text=auto eol=lf`. На Windows без него git видит
   весь репозиторий изменённым из-за CRLF, и настоящие правки тонут в шуме.
4. **`.gitignore` и `.env.example`** — секретов в репозитории нет никогда;
   пример конфига есть всегда.
5. **`docs/` с двумя файлами** — назначение и границы продукта, и **реестр
   инсайтов** с условиями срабатывания. Реестр заводится сразу: он нужен,
   чтобы отклонённая идея не была потеряна и не стала scope creep.
6. **Контракт и его тест.** Что именно зафиксировано навсегда (коды, схема,
   формат ответа) — и тест, который это стережёт. Тест пишется на контракт,
   не на текущий список.
7. **CI** — прогон тестов на push. До того, как появится что ломать.
8. **Память Claude** — `/projects/<id>/overview.md` (что за проект, стек,
   состояние) и `ways-of-working.md` (как работаем). Без этого каждая новая
   сессия начинается с археологии.

**Done when:** новый участник (или новая сессия Claude) по этим восьми файлам
понимает, что делать, не задавая вопросов.

## 6. Старт подпроекта внутри существующего

Подпроект — это не новый репозиторий, а новая **зона ответственности** внутри
него (плагин, агент, слой). Комплект короче:

1. Запись в `docs/` — зачем он и где его граница.
2. Каталог по правилам §3.
3. Собственный `README.md`, если у подпроекта своя точка входа.
4. Ответ на вопрос «какой контракт он добавляет» — или явное «никакого».
5. Строка в реестре (`agents/registry.py`, `book/registry.py`), если подпроект
   добавляет навык или лист. Состав — данные, не код.

Токен `OM*` открывает сессию проекта; старт подпроекта проговаривается явно и
проходит эти пять пунктов до написания кода.

## 7. Открытые решения, которые блокируют развитие

Фиксируются здесь, чтобы не всплывали каждый раз заново.

| Решение | Что блокирует | Состояние |
|---|---|---|
| Лицензия: что открыто, что закрыто | Публикацию продуктового плагина `dfm` | **Не принято.** Стандарт, который никому нельзя использовать, стандартом не станет; движок при этом закрывать разумно |
| Аутентификация и изоляция воркспейсов | MCP-сервер над `/api/assumption-sets/{project}` | В плане, предусловие пилота |
| `ANTHROPIC_API_KEY` в Vercel | LLM-навыки на проде работают только через fallback | Не сделано |

---

## 8. Чего в протоколе намеренно нет

- **Автоматического создания репозиториев.** Технически невозможно из
  контейнера и не нужно: это одна кнопка в GitHub Desktop.
- **Требования делать плагин на каждый проект.** Плагин оправдан, когда
  процедура повторяется в третий раз, — не раньше.
- **Единого стандарта финмодели.** Стандарты множественны и настраиваются
  пользователем; как именно — в `docs/Профили_стандарта_и_выбор.md`.
