# Продуктовая стратегия и реестр инсайтов

Правило: **один критический путь, всё остальное — в реестр с триггером.**
Инсайт, попавший в реестр, не потерян — он ждёт своего триггера. Инсайт,
не попавший в реестр, потерян. Поэтому реестр пополняется в конце каждой
рабочей сессии.

## Северная звезда (до тестирования и инвестраунда)

**Документ «переворачивается» в финмодель по нашей схеме.**

PDF / DOCX / XLSX / CSV / PPTX / Google Sheets
→ извлечение существенных данных с сохранением структуры и источников
→ допущения по схеме `assumptions.v1` (auto / AI / manual)
→ книга модели по нашему реестру листов
→ выгрузка Excel / Google Sheets.

Критический путь (порядок жёсткий, ничего между пунктами не вставляем):
1. Схема допущений (pydantic + БД, версионирование на проект)
2. Экстрактор документов (LLM, выход строго по схеме, каждый факт с источником)
3. Валидатор (арифметика, сверка документов между собой, список «требуют уточнения»)
4. Форма допущений в workspace v2 (auto/AI/manual) + память предпочтений
5. Генерация книги по sheet registry + экспорт
6. Тестирование на 3–5 реальных кейсах → материалы для раунда

Критерий «размениваемся на мелочи»: если задача не приближает ни один из
шести пунктов — она идёт в реестр, а не в работу.

## AFM&C — Agentic Financial Modelling & Controlling

Ключевое слово — **agentic**. Не «автоматизированное моделирование»
(конвейер: документ вошёл, файл вышел), а модель, вокруг которой живут
агенты с ролями, инструментами и памятью. Файл — снимок; продукт — процесс.

**Три роли агентов (M, A, C):**

1. **Modelling-агент** — строит: собирает допущения из документов и диалога,
   задаёт недостающие вопросы, применяет память предпочтений, генерирует
   книгу по реестру листов. Пользователь общается с агентом, а не заполняет
   форму; форма — лишь способ подтвердить то, что агент понял.
2. **Audit-агент** — проверяет: сверяет модель с пакетом документов и
   требованиями банка, находит расхождения (кейс теплиц: CAPEX, НДС,
   взносы — найдено агентом за минуты), формирует мотивированное заключение
   со ссылками на источники. Работает и на нашу модель, и на чужую (И-1).
3. **Controlling-агент** — сопровождает: после утверждения модели
   непрерывно сверяет план с фактом (выписки — И-2, отчётность),
   пересчитывает ковенанты, сигналит об отклонениях до того, как они
   стали проблемой, предлагает пересмотр допущений. Controlling здесь —
   в управленческом смысле (контроллинг), не только «контроль».

**Что тогда является стандартом.** Не формат файла, а **контракт между
агентами**: схема допущений (`assumptions.v1`), структура книги
(sheet registry) и протокол доступа. Практически это MCP-интерфейс модели:
модель публикует инструменты (получить допущения, пересчитать сценарий,
проверить ковенанты, объяснить показатель со ссылкой на источник), и
любой внешний агент — прежде всего агент банка — работает с ней напрямую.
Кредитный конвейер банка спрашивает у модели заёмщика «покажи DSCR по
кварталам при ставке +3 п.п.» и получает воспроизводимый ответ вместо
недель переписки с аналитиком. Диалог agent-to-agent — то, чем XBRL был
для отчётности, но для живых моделей.

**Путь внедрения:** (1) открытая спецификация схемы и протокола —
референсный валидатор публичен, экосистема инструментов наша;
(2) первый банк подключает audit-агента к своему конвейеру — экономит
экспертизу, задаёт стандарт подачи; (3) сетевой эффект: заёмщики подают
AFM-модели, потому что их рассматривают быстрее, банки требуют AFM,
потому что проверка дешевле; (4) монетизация по ролям: M — SaaS-подписка
конструктора; A — API-тарификация проверок для банков и консультантов;
C — recurring-подписка на мониторинг (модель живёт после выдачи кредита);
(5) защита позиции — стандарт скопируют, экосистему нет: память
предпочтений, отраслевые профили, база требований банков, накопленные
кейсы аудита.

Практический шаг нулевой стоимости уже действует: `assumptions.v1` и
sheet registry ведём как публичные (чистые имена, версии, changelog),
а движок проектируем так, чтобы каждая способность агента была отдельным
вызываемым инструментом — тогда MCP-обвязка в нужный момент — операция
на дни, не месяцы.

## Решения по обучающей паре (теплицы)

Пара «бизнес-план PDF + модель XLSB» — обучающий материал. Решения:
истина для фикстур — XLSB (расчётный эталон, против него валидируется
извлечение); расхождения PDF↔XLSB не «чинятся», а сохраняются как
эталонный тест-кейс audit-агента. В схеме допущений налоговые ставки —
расписания во времени (пример: НДС 20% → 22% с даты), чтобы подобные
развилки были параметром, а не конфликтом версий. Конфиденциальные файлы
в репозиторий не попадают; фикстуры — синтетический аналог той же структуры.

## Порядок работы с реестром

В конце сессии: новые инсайты → в таблицу. Начало сессии: проверить,
не сработали ли триггеры. Изменение критического пути — только осознанным
решением с записью причины здесь же.
