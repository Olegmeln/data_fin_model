# Аудит модели

Работает в двух режимах: проверка собственной книги DFM перед сдачей блока и
аудит внешней модели, пришедшей от заёмщика или консультанта. Набор контролей
один и тот же — меняется только то, откуда берутся адреса.

Структура книги — `/dfm:model-book`. Профиль и обязательное ядро —
`/dfm:model-profile`.

---

## 1. Лист Checks

Строка проверки: `check_id`, Раздел, Описание, Допуск, Расхождение, Статус.

Расхождение считать по **всем** периодам, а не по последнему:

```
SUMPRODUCT(MAX(ABS(...)))
```

Допуск `0.5` для балансовых проверок, `0` для ошибок.

Сводный статус вверху листа. При `FAIL` — **остановиться**, показать
расхождение и его источник, дальше не идти. Продолжение работы поверх
несошедшегося баланса умножает разбор потом.

---

## 2. Обязательный набор контролей

| Контроль | Что ловит |
|---|---|
| баланс | актив ≠ пассив |
| денежные средства | остаток CF ≠ строке баланса |
| нераспределённая прибыль | накопленная прибыль ≠ строке баланса |
| долг | график погашения ≠ остатку долга |
| амортизация | начисление ≠ движению по основным средствам |
| оборотный капитал | изменение ОК ≠ вкладу в CF |
| ошибки в итоговых блоках | `#REF!`, `#DIV/0!`, `#VALUE!`, `#N/A` |
| входящий баланс | стартовые остатки не сходятся |
| незаполненные допущения | обязательный вход пуст |
| хардкоды | константа там, где должна быть формула — через `ISFORMULA` |

Последний контроль важнее, чем кажется: хардкод не ломает модель сегодня и
ломает её через месяц, когда допущение поменяли, а число осталось.

---

## 3. Главное правило верификации

**Проверка на нулях ничего не доказывает.** Нулевой баланс сходится
тривиально, IRR и окупаемость не вычисляются, все плитки покажут ноль.
Модель, «прошедшую проверку» на пустых допущениях, не проверяли.

Порядок:

1. Заполнить допущения тестовым набором — не нулями и не единицами:
   значениями разного порядка, чтобы ошибки масштаба стали видны.
2. Проверить контроли и ключевые показатели.
3. **Вернуть значения к пустым.**
4. Подтвердить, что все статусы снова «требует заполнения».

Шаг 3 пропускают чаще всего — и отдают книгу с тестовыми числами внутри.

---

## 4. Негативный тест контроля

Контроль, который никогда не срабатывал, не проверен. Для каждого:
подменить ячейку константой и убедиться, что проверка переходит в `FAIL`,
затем вернуть формулу.

Контроль, не переходящий в `FAIL` при заведомо сломанном входе, — это не
контроль, а украшение.

---

## 5. Чтение книги при проверке

Итоговые листы проверять **перечислением из коллекции книги**, а не по списку
из памяти: список в памяти отражает то, что вы собирались сделать, коллекция —
то, что получилось.

То же для диапазонов: если диапазон не перечитан после записи, он не проверен,
и в отчёте это надо сказать прямо.

---

## 6. Аудит внешней модели

Отличия от проверки своей книги:

1. Адреса неизвестны — сначала карта: какие листы, где периоды, где итоги.
2. Извлечь допущения в набор `assumptions.v1`, отметив источник каждого
   значения (лист, ячейка).
3. Прогнать тот же набор контролей из §2 по найденным адресам.
4. Отдельно — сверка с пакетом документов: бизнес-план, смета, КП.
   Расхождения между документом и моделью ценнее внутренних: они означают,
   что модель не соответствует заявленному проекту.

Типовые находки на реальных кейсах: итог CAPEX не совпадает со сметой, ставка
НДС отличается между листами, взносы с ФОТ посчитаны по устаревшей ставке.
Искать в первую очередь их.

---

## 7. Отчёт по итогам блока

1. Изменённые листы и диапазоны
2. Новые именованные диапазоны и таблицы
3. Результат проверки формул
4. Незаполненные обязательные входы
5. Записи журнала `DEV_LOG`
6. Статус: `READY FOR FORMULA AUDIT` или `REQUIRES REVIEW`
7. Явно: какие диапазоны перечитаны для верификации, а какие нет

Пункт 7 не декоративный. Без него отчёт утверждает больше, чем проверено.
